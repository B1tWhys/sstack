# Plan: groundwork for the GUI

The goal is a GUI good enough that the person can work on sstack in it, in place of the TUI. The design is settled in `docs/adr/0009-gui-in-iced-over-the-same-core.md`; read it, ADR-0004, `GLOSSARY.md` and `AGENTS.md` before starting a step.

## How to run a step

Each step is done by one agent with a fresh context, in order, because each step builds on the one before it. Do only your step.

1. Read this file, the documents above, and the code your step names.
2. Make the change test-first where the step adds behaviour. Steps 2 to 5 are refactors: the TUI and headless mode must behave exactly as before, and every existing test and snapshot must pass unchanged.
3. Before merging, extracting or copying any code, load the `judging-duplicate-code` skill and apply its test.
4. Run `cargo nextest run --workspace --all-features` and commit with a conventional commit message. The hooks must pass, which includes every function's CRAP score being 6 or less. Never bypass them and never push.
5. Tick your step below and write a short note under it: anything the next step needs to know, and anything you found that this plan got wrong.

A step is done when its commit is in, the full test run is green, and its note is written. If the step cannot be done as written, stop, leave the code as it was, and explain why in the note.

## Steps

### [x] 1. Lock the Session log

A Running Harness holds an exclusive lock on a Session's log for as long as it has the Session open, so that two Harnesses can never append to the same log. Take the lock with `File::try_lock` in `SessionLog::create` and `SessionLog::open` (`crates/core/src/session.rs`), and add a `SessionError` variant whose message is "this Session is open elsewhere". Reads that only look at a log, such as `first_prompt` and `is_parked`, take no lock. Check that the TUI and headless mode show the error well. Test that opening a log a second time in the same process fails.

Note: The variant is `SessionError::OpenElsewhere`. I added `session::lock_free_read(path)`, a lock-free read of everything recorded so far, because many tests read a log back while an Agent still had it open. Use it, not `SessionLog::open`, wherever code only looks at a log. The lock lasts as long as the `SessionLog`. In the TUI that means as long as the worker task holding the `Agent`, which can outlive the `App` by a few polls. The test harness in `tui/app.rs` therefore has a `stopped()` helper that waits for the event channel to close before a test relaunches into the same Session. A real Rebuild needs nothing extra, because Rust opens files close-on-exec and the `exec` in `rebuild.rs` releases the lock. I checked the messages by reading the code rather than running a second Harness. At startup, headless mode and the TUI print `error: this Session is open elsewhere` before the TUI takes the terminal. Inside the TUI, the person sees `could not open the Session: this Session is open elsewhere` when switching to a Session that is open elsewhere, or `could not carry on a Session: ...` for a parked one. A GUI and a TUI on the same project can now list each other's Sessions but not open them.

### [x] 2. Move the lifecycle, Human Commands and Rebuild into core

Move `crates/cli/src/tui/lifecycle.rs` (`SessionState`, `SessionEvent`, `Phase`, `Trigger`, `Effect`, `Exit`, `interrupt`), `crates/cli/src/command.rs` and `crates/cli/src/rebuild.rs` into the `sstack` crate. Rebuild currently hardcodes `--package sstack-cli` and the binary `sstack`. Make it build and relaunch the package and binary that is running, given by the caller.

Note: The new modules are `sstack::human_command` (`Command`, `parse_command`), `sstack::running_harness` (`SessionState`, `SessionEvent`, `Phase`, `Trigger`, `Effect`, `Exit`, `Interrupt`, `interrupt`) and `sstack::rebuild` (`Binary`, `build`, `relaunch`). `rebuild::build` takes a `rebuild::Binary`, which gives the cargo package and the binary's name. The CLI passes its own as the `HARNESS` const in `crates/cli/src/lib.rs`: package `env!("CARGO_PKG_NAME")`, binary `sstack`. The GUI should define its own the same way, with `sstack-gui` for both. Rebuild still finds the Harness Source from core's own `CARGO_MANIFEST_DIR`, and the profile from `cfg!(debug_assertions)` in core. Both match the binary because every crate sits in one workspace and is built with one profile. `Phase::progress` did not move: it is now the function `progress` in `tui/app.rs`, because its text names Alt-C. For the same reason, the docs in `running_harness` speak of an interrupt and an interface, not Alt-C and the `App`. `Command` still has variants only the TUI acts on (`New`, `NewMain`, `Archive`, `Vim`, `Rename`), so step 5's controller has to pass those back to the interface. `relaunch_args`, which gives the arguments for the relaunched binary, is still in `setup.rs` and moves with step 4.

### [x] 3. Split the Session reports out of the TUI's events, and move the Turn runner

`tui::Event` (`crates/cli/src/tui/event.rs`) mixes terminal input (`Key`, `Paste`, `Resize`, `Scroll`, `Click`, `Vim`) with reports about a Session (`Resumed`, `TurnStarted`, `TurnContinued`, `Agent`, `TurnEnded`, `Approval`, `BuildFinished`, `Notice`). Move the reports into core as their own type, with `ApprovalRequest` and `Reply`. The TUI keeps its `Event` and wraps the core type. Then move `AgentHandle` (`crates/cli/src/tui/worker.rs`) into core, reporting through the new type.

Note: The reports are `sstack::session_report::SessionReport`, with the same eight variants the TUI had. `ApprovalRequest` and `Reply` sit beside it. Core reports through a `ReportSender`, which is a cloneable wrapper around a function `Fn(SessionReport) + Send + Sync` that the interface chooses when it creates one with `ReportSender::new`. The function must not block, because core calls it from inside a Turn's event callback. The TUI's `Event` has one `Event::Report(SessionReport)` variant in place of the eight. `SessionSender::reporter` returns a `ReportSender` whose reports arrive as `Event::Session(id, Event::Report(..))`, on the same channel as before, so ordering is unchanged. The GUI can make its own with a closure that sends into a channel its `Subscription` reads, and can tag reports with a window or Session id there. `AgentHandle` is now `sstack::turn_runner::AgentHandle`, and `AgentHandle::spawn` takes the agent and a `ReportSender`. I also moved the TUI's `EventApprover`, the Approver that sends an `ApprovalRequest` and waits for the `Reply`, into core as `session_report::ReportingApprover`, because the GUI asks about shell commands in exactly the same way. For step 4, `prepare` still takes a closure that makes an Approver for a Session id, and the TUI builds `ReportingApprover::new(SessionSender::new(id, ..).reporter())`. The core setup can take a `ReportSender` per Session instead. `BuildFinished` and `Notice` are not about any one Session's Turns. The TUI sends `BuildFinished` straight on its event channel, not wrapped in `Event::Session`, and only shows `Notice` on a Pane by calling `update` directly; core sends neither yet. Step 5's controller will be the first core code to produce them.

### [x] 4. Move the setup of a Session into core

Move `crates/cli/src/setup.rs` into core, except for anything that reads the clap `Args`, which stays in the binaries. Core takes plain values: which Session to start or resume, the Connection and model if overridden, and where the Session works. `describe.rs` holds the words headless mode and the TUI show for what happens in a Session. It is presentation, so it stays in the CLI crate.

Note: The module is `sstack::session_setup`. Its entry point is the `bon` builder `prepare()`, which takes `start` (a `Start`, with `Place`), `directory` (the directory the person started in), the optional `connection` and `model` (set them with `maybe_connection` and `maybe_model` from an `Option<&str>`), `approver` (a closure that makes an Approver from the Session id) and `containers`. It returns a `Run` or a `SetupError`, whose messages match the old anyhow ones. `main_checkout`, `sessions_directory` and `installed_skills` take the start directory too, so core no longer reads the current directory. `LATEST` moved into core, and the CLI's `--resume` default names it from there. A binary must still supply four things itself: the start directory (both binaries pass `std::env::current_dir()`), the approver, the shared `Containers`, and the words for `Run::descriptions_left_out`. That field is the count of Skills listed without their descriptions. The TUI turns it into a notice with `describe::listing_shortened` and appends it after `Run::notices`, in the same order as before. The GUI should show a similar warning in words of its own. `relaunch_args` stayed in the CLI, because it writes out the CLI's own flags. It is now `Args::relaunch` in `crates/cli/src/lib.rs`, with its test. Step 6 decides, through `judging-duplicate-code`, whether the GUI shares the flag definitions and this method or writes its own. The `dirs` dependency moved from the CLI crate to core.

### [x] 5. Pull a controller for one Session out of the TUI's App

`App` (`crates/cli/src/tui/app.rs`) mixes the screen with logic that every interface needs. Move that logic into core as a controller for one Session. It covers `submit`, which decides whether a line is a Human Command, a Skill or a prompt, `advance`, `check_settled`, `interrupt`, `resume_parked`, `build_finished` and the Phase they drive. The interface tells the controller what the person did and what core reported, and carries out what the controller asks for. Everything about several Sessions at once stays in the TUI: the sidebar, `queue`, `step`, `show_longest_waiting`, `open_new` and archiving. So do `/rename` and `/vim`. Load the `codebase-design` skill before choosing the controller's interface. If the seam is unclear, stop and describe the options in the note.

Note: The plan was wrong to put the Phase in a controller for one Session. One Phase covers every open Session: a quit or a Rebuild waits until no open Session has a Turn running, and then stops all of them. (Since ADR-0012, a Rebuild no longer waits for the person to approve a shell command. It puts the question off, and the Turn parks and asks it again later.) So the controller is two types.

- `sstack::session_controller::SessionController` is one open Session. It holds the `AgentHandle`, the `SessionState` and the Skills. Its public calls are `new(agent, skills, parked)`, `state()`, `answered()` (the person answered a shell command question), `continue_parked()` and `set_paused()`. The busy check, the Skill lookup and the state machine changes on reports are crate-internal, so an interface can only reach them through the Running Harness.
- `sstack::running_harness::RunningHarness` holds the Phase. An interface keeps one per process. For something that happened in one Session, call `harness.in_session(&mut focus, &mut others)` and then one of `submit(line)`, `report(&report)` or `interrupt()` on the `InSession` it returns. `others` is every other open Session, reached through the `OpenSessions` trait. Its one method, `visit`, calls a closure on each `SessionController`. For things that concern no single Session, call `build_finished(built, &mut all)` and `relaunch_failed(&mut all)`, and read `phase()` for any progress text.

Each call returns `Option<Outcome>`, and the interface carries it out. The variants are `TurnStarted(text)` (the TUI names the Session from it at once), `Refused(Refusal)`, `Command(..)` (only `New`, `NewMain`, `Archive`, `Vim` and `Rename` come back), `StartBuild`, `CancelBuild` and `Exit`. A `Refusal` is data, not words. The TUI's `refusal_text` words it, because `Busy` and `Draining` name Alt-C. So core still sends no `SessionReport::Notice`. Core sends no `BuildFinished` either, because the interface runs the build itself when asked with `StartBuild`. That keeps tests from running cargo.

The GUI in step 6 has one Session per window. It passes `&mut NoOtherSessions` as `others`, and the `SessionController` itself as `all`, since `SessionController` implements `OpenSessions`. It runs `rebuild::build` as an iced `Task` on `StartBuild`, and passes the binary, or `None` on failure, to `build_finished`. It reads `session::is_parked` to give `new` the `parked` flag, and calls `continue_parked` once the Session is open. The core tests in `session_controller.rs` show these calls with reports fed by hand.

In the TUI, a `Pane` holds an `Option<SessionController>`, because a stored Session has no agent until it is shown. `Pane::control` runs a closure on the controller and updates the waits that order the sidebar from the state before and after. `App::drive` splits the panes into the focused one and the rest, which go to core as a `Panes` adapter. `in_session` exists because the clippy limit is three arguments, and it reads better than a `bon` builder on each call. The TUI's small `Happened` enum picks the `InSession` call, because clippy's `redundant_closure_for_method_calls` suggests `InSession::interrupt` for `|harness| harness.interrupt()`, and that path does not compile against the higher-ranked closure.

### [x] 6. Add the GUI crate

Add `crates/gui`, package `sstack-gui`, with a binary of the same name, built on the latest iced release. It takes the TUI's `--resume`, `--connection` and `--model` flags, and works on the project in the directory it is started from. Apply `judging-duplicate-code` before sharing the flag definitions with the CLI. It opens one Session in one window, with a plain multi-line prompt that runs a Turn through the controller, and shows the reply as plain text. Session reports reach the iced app through a `Subscription`. Keep styling to iced's defaults: the visual style gets a session of its own.

Test the logic by feeding `Message`s to `update` and checking state. Add a few `iced_test` tests that drive the real widgets and check structure and text. Add no pixel snapshots yet.

Note: The crate uses iced 0.14.0 and iced_test 0.14.0, the latest on crates.io. iced has its `tokio` feature on, so iced runs `boot`, `update` and subscriptions inside its own Tokio runtime, which `AgentHandle::spawn` needs. Like the CLI, the crate is a library with the docs and a binary `sstack-gui` with `doc = false`. `lib.rs` has `Args`, `ready` (which calls `prepare`) and `application`, which builds the iced program. `reports.rs` has `Reports`. `window.rs` has `Window`, its `Message` and the transcript's `Block`, with its tests in `window/tests.rs`. `test_support.rs` readies a Session on a `ScriptedProvider`.

The GUI defines its own flags. By `judging-duplicate-code` they are not duplicate: ADR-0009 expects the GUI to choose a project and a Session itself later, and then its flags change while the TUI's stay. I did not write `Args::relaunch` yet, because only Rebuild needs it. Step 7 should write the GUI's own, for the same reason.

The Session is readied before iced starts, so a failure such as "this Session is open elsewhere" prints `error: ...` in the terminal and no window opens. iced's `boot` is an `Fn`, so `open` takes the `Run` out of a `Cell`. `Window::open` makes the `Reports`, a futures unbounded channel whose sending half is the Session's `ReportSender`. `Window::subscription` is `Subscription::run_with(reports, Reports::stream)`, hashed by the Session id, and each report arrives in `update` as `Message::Report`. The test `reports_reach_the_window_through_its_subscription` in `lib.rs` runs the real program in `iced_test::Emulator` and times out if the subscription delivers nothing.

Run it from inside the project with `cargo run -p sstack-gui -- [--resume [id]] [--connection name] [--model id]`. Without `--resume`, every launch starts a new Session in a worktree of its own. The TUI reuses a blank, unnamed Session instead, so the GUI may want the same rule. I could not see a window, so I only checked that the binary builds, that `--help` works, and that `--resume` with an unknown id prints an error and exits with 1. `update` tests send `Message`s and pass on reports from `window.reports.stream()` by hand. The `iced_test` `Simulator` renders headless with tiny-skia in about 0.3 seconds a test. Its selectors cannot read a `text_editor`'s content, only find the editor by its id, `PROMPT`, so tests read the prompt from `Window::prompt`.

What step 7 should know:

- Shell commands the Sandbox cannot run are denied, because `ready` passes `DenyAll`. `prepare` calls the approver closure with the Session id before `Window::open` makes the `Reports`. To use `ReportingApprover`, make the `Reports` inside that closure and hand them to `Window::open` with the `Run`.
- `/rebuild` lands in `Window::refuse_rebuild`, which calls `build_finished(None, ..)` at once. Replace it with a `Task` that runs `rebuild::build` on a `HARNESS` const naming `sstack-gui` as package and binary, made abortable for `Outcome::CancelBuild`. `carry_out` maps every `Exit` to `iced::exit()`, so `Exit::Rebuild` has to relaunch instead.
- Nothing calls `InSession::interrupt` yet, and no key does anything. The prompt is sent only by the Send button.
- `Block::Reply` joins the text of every Step in a Turn. Tool calls, reasoning, the entries in `SessionReport::Resumed` and the ends of a Turn other than an error are not shown, and the transcript does not scroll to follow a reply.
- Closing the window ends the process with any Turn still running, without a drain. `exit_on_close_request(false)` with `iced::window::close_requests` could route a close to `/quit`.

### [x] 7. Make the GUI usable for work on sstack

Commit each item separately:

- A transcript that streams the reply as it arrives, shows the model's reasoning, and shows each tool call as a one-line summary. The GUI builds its own transcript from the Session reports; ADR-0009 explains why it does not share the TUI's.
- Approval of a shell command, for when the Sandbox is unavailable.
- Interrupting a running Turn.
- Rebuild, by `/rebuild` and by a button, which relaunches `sstack-gui` into the same Session.

After this step the person can work on sstack in the GUI.

Part 1, transcript: The transcript is `Transcript` in `crates/gui/src/transcript.rs`, with its `Block` kinds `Prompt`, `Reply`, `Reasoning`, `Tool` and `Notice`. `Transcript::report` shows a `SessionReport` and returns whether anything shown changed. The entries in `SessionReport::Resumed` go before the setup notices, because they happened before the window opened. Reasoning and the reply of each Step stream into blocks of their own. A tool call is one unwrapped line, `Tool: name input`, with the input cut at 100 characters and ` (failed)` added when it failed. `ToolFinished` marks the newest call, since tools run one at a time. On resume, the call is found by its id. Turn ends other than `Finished`, errors and `ContextNearLimit` are notices. The labels are `> `, `Thinking: ` and `Note: `, and a reply has none. By `judging-duplicate-code`, none of this is shared with the TUI's transcript or `describe.rs`, and the module docs say why.

The window shows the prompt it sent when `submit` starts a Turn, and ignores `SessionReport::TurnStarted`. A Skill therefore shows as the `/name` line typed, but a resumed Session shows the whole loaded Skill text from `Entry::User`. Following works through `Message::Scrolled { at_end }`, which the scrollable's `on_scroll` sends. When the transcript changes while `following` is set, `Window::report` returns `operation::snap_to_end(TRANSCRIPT)` batched with whatever the Running Harness asked for. Starting a Turn follows again. So a report that changes the transcript now gives a `Task` with one more unit, which matters to tests that count units to spot `iced::exit()`.

For the next parts: put an approval in the transcript with a new `Block`, or beside the prompt, and send the answer through `SessionController::answered`. `SessionReport::Approval` reaches `Transcript::report` already and falls through to `_ => false`. A cancelled Turn already shows "the Turn was cancelled", so the interrupt part need only call `InSession::interrupt`. Tests that read reports across several Turns must take `window.reports.stream()` once and use `until_turn_ends_on`, because a second stream is empty.

Part 2, approvals, interrupt and closing: `Reports::new()` no longer takes the Session id. iced tells one subscription from another by where the channel sits in memory, so `ready` can make the `Reports` before `prepare` and give one `ReportSender` to both `ReportingApprover` and the Turns. `ready` returns a `window::Ready` with the `run`, `reports` and `sender`, and `Window::open` takes it. `test_support::readied` returns a `Ready` with a `ReportingApprover` too, and `bash_call` scripts a shell command. The test Sandbox is off, so every such command is asked about. The window keeps its open questions in `Window::questions` and shows the oldest above the prompt: the note, ``Run `command`?``, and Allow and Deny buttons that send `Message::Answer(bool)`. The answer goes to the question's `reply` and then to `SessionController::answered`. A Turn that ends drops its questions. A question dropped unanswered denies the command, so closing the window never leaves a Turn waiting. By `judging-duplicate-code`, the TUI's `Approval` component is not shared: it answers by key and draws a popup, and the few lines that keep the queue are not worth the coupling.

Escape and an Interrupt button send `Message::Interrupt`, which calls `InSession::interrupt` and passes the outcome to `carry_out`. Escape comes from `keyboard::listen`, which only hears keys no widget kept. The prompt drops focus on Escape without keeping the key, so Escape works while typing. With nothing running, Escape quits, as Alt-C does in the TUI. The button is disabled unless a Turn is running or the Running Harness is draining, so a click cannot quit. `iced_test`'s `Emulator` never passes input to subscriptions, so the tests check that the prompt leaves Escape `Ignored` and test `interrupt_key` apart.

`application` sets `exit_on_close_request(false)`, and `Window::subscription` maps `window::close_requests` to `Message::CloseRequested`, which calls `submit("/quit")`. A second close or `/quit` while waiting quits at once, and interrupting carries on. While draining to quit, `progress` shows a line above the prompt saying so. No test can send a real close request, and I could not see a window, so the wiring in `application` is checked by reading only.

What the Rebuild part should know:

- `carry_out` still maps every `Exit` to `iced::exit()`, ignores `CancelBuild` (an interrupt during a Rebuild's drain returns it), and ignores `Refused`.
- During `DrainingToRebuild`, `submit("/quit")` is refused with `Refusal::Draining`, so a close does nothing at all. Decide what a close means then, for instance backing out of the Rebuild and quitting, and give that drain a line in `progress`, which returns `None` for it now.
- The Interrupt button is enabled during any drain, so it already backs out of a Rebuild.
- A model response with no text before its tool calls leaves an empty `Block::Reply` in the transcript, because `ScriptedProvider` sends `Text("")`. Check whether a real Provider does the same before hiding empty replies.

Part 3, Rebuild: `/rebuild` and a Rebuild button build `sstack-gui` and relaunch it into the same Session. `Ready` has two more fields. `build` is a `window::Build`, a function that returns the build as a boxed future of `Result<PathBuf, String>`. `ready` passes `build_harness`, which runs `rebuild::build(HARNESS)`, and `HARNESS` in `lib.rs` names `sstack-gui` as package and binary. `test_support::readied` passes `never_built`, a future that never ends, so no test runs cargo and tests send `Message::Built` themselves. A test that needs a build to finish by itself opens its window with `building_with(built_at_once, ..)`. `produced` in `window/tests.rs` runs a `Task` through `iced_test::runtime::task::into_stream` and returns the messages it sends.

On `Outcome::StartBuild`, the window runs the build as an abortable `Task` and keeps its handle in `Window::building`. `CancelBuild` aborts it, and the build's `kill_on_drop` then stops cargo. A `Message::Built` that arrives after the build was stopped is ignored. A failed build shows cargo's error as a notice, and the Session carries on. `progress` has a line for building and one for built, which shows only while a Turn is still running. The Rebuild button sends `Message::Rebuild`, which submits `/rebuild` without touching the prompt, and is disabled during any drain.

`Exit::Rebuild(binary)` puts the binary in `Ready::relaunch`, an `Arc<OnceLock<PathBuf>>`, and returns `iced::exit()`. `run` reads it once iced's `run()` has returned, when the window and the event loop are gone, and calls `rebuild::relaunch` with `Args::relaunch`: `--resume` with the Session id, and `--connection` and `--model` if given. The GUI has its own `Args::relaunch`, kept apart from the CLI's for the same reason as the flags. If the exec fails, `run` returns `could not relaunch into <path>: <error>`, which prints as `error: ...` and exits with 1. The GUI cannot reopen by running iced a second time, because winit refuses a second event loop in one process (`EventLoopError::RecreationAttempt`). To reopen, it would have to exec from inside `update` while the window is still open, and on failure call `RunningHarness::relaunch_failed` and carry on, as the TUI does. That gives up tearing the window down before the exec.

Closing the window during a Rebuild backs out of it, which stops the build, and then submits `/quit`. The phase is then `DrainingToQuit`, so a second close quits at once. `Window::close` alone makes this choice, so a close can mean something else during a Rebuild by changing only that function. One cost: backing out carries on any Turn that had already parked to wait for the build, because core's `Effect::Abandon` resumes parked Turns. That Turn parks again at the end of its next Step, so the quit can wait one Step longer than a plain quit. Avoiding that would need a core transition from `DrainingToRebuild` straight to `DrainingToQuit`.

`Transcript::reply` now ignores empty text, so a response with no text before its tool calls leaves no empty `Block::Reply`. The Anthropic Provider turns each genai `Chunk` into `StreamEvent::Text`, and I did not check whether a chunk can be empty. The guard does no harm either way.

`cargo build -p sstack-gui`, and the exact `cargo build --package sstack-gui --profile dev` that a Rebuild runs, put the binary at `target/debug/sstack-gui`, the path `rebuild::build` computes from core's `CARGO_MANIFEST_DIR`. I could not see a window, so these were checked by reading only: that iced's `run()` returns on macOS after `iced::exit()` (iced_winit returns after `run_app`, and winit 0.30 says only iOS and the web never return), the exec into the new binary from a real window, and that aborting the build kills cargo. The tests check the button and the progress lines through `iced_test`'s simulator, not by eye.
